DEFINITIVE: full-param 4B PPO does NOT fit on one 80 GB H100 with this pipeline (3 attempts, all in train_h100_fullft.log): (1) 32K seq / vLLM 0.45 → OOM in `loss.backward()`; (2) 8K seq / vLLM 0.30 → OOM in `optimizer.step()` `torch._foreach_sqrt` (Adam state); (3) 8K / vLLM 0.20 / expandable_segments:True → vLLM `init_engine` FAILS (16 GB < 4B vLLM floor). Code-confirmed why: verl builds plain on-GPU `optim.AdamW` (verl/workers/fsdp_workers.py:369) and calls `load_fsdp_optimizer(device_id=cuda)` (:663) before every update — the ~48 GB fp32 Adam+master state is GPU-resident DURING `optimizer.step()` regardless of seq len; `optimizer_offload` only frees it BETWEEN steps. No built-in CPU/8-bit-Adam path. vLLM init floor ~24 GB + ~48 GB optimizer + params/grads > 80 GB from both sides. Paper's 2x8=16 GPUs shard the optimizer via FSDP (~3 GB/GPU) + ulysses for long seq — fundamentally multi-GPU. So on ONE GPU, LoRA is the only working full-pipeline (matches the original L40S conclusion). The committed `train_comprehensive_swerebench_l40s.sh` (LoRA r32) is the runnable single-GPU artifact; it completed GRPO step:1 on this H100 too. `train_comprehensive_swerebench_h100.sh` documents the paper recipe + the single-GPU impossibility in its header (NOT runnable for full-param on 1 GPU as-is). Open single-GPU full-FT paths (need user buy-in, all non-trivial): patch verl to a true CPU-step optimizer / bitsandbytes 8-bit Adam; or get a multi-GPU box. The LoRA step:2 blocker (LoRA↔vLLM `wake_up` KeyError `...base_layer.weight`) is the thing to fix for a multi-step single-GPU run.
